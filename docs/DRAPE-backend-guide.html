1What DRAPE is

DRAPE (“Wear once, don’t buy”) is a hyperlocal, peer-to-peer clothing rental network for Chennai. People who own an outfit they wore once list it; people who need an outfit for one evening describe what they need in plain language and get ranked matches a few kilometres away.

The backend exists to make two flows feel effortless, and to keep them honest:

Flow A · List a piece

Snap a photo. The server stores it and asks a vision model to draft the tags (title, category, occasions, style, colours, formality, description). The lister edits the draft, sets size, price per day and pickup area, and publishes. The server embeds the listing so it is searchable immediately.

Flow B · Describe what you need

“Something for my friend’s sangeet, M, under ₹800.” A text model turns that into filters plus a style description; the description is embedded; Postgres filters by size, budget, gender and distance and ranks by vector similarity. If nothing good is close, a fallback ladder relaxes the search and says exactly what changed.

Around these flows sit three supporting features:

  • Bookings. A borrower picks dates (up to 14 days, up to 90 days ahead) and pays a 20% advance (minimum ₹50). The server recomputes the price; a Postgres exclusion constraint makes double-booking impossible.
  • Owner notifications. When a booking is inserted, a database trigger writes a notification for the listing’s owner in the same transaction. The owner’s header bell shows it with the borrower’s contact.
  • Complete the look. For any listing, the API suggests complementary pieces (bottoms for a top, layers for a dress) that share an occasion and a style.

2Architecture at a glance

There are only four moving parts: a static single-page app, one serverless function, one Postgres database with file storage, and two AI providers. Everything that needs a secret runs inside the function.

Why one function?

Vercel’s Hobby plan allows at most 12 serverless functions per deployment, and DRAPE has more than 20 endpoints. So every route lives in api/_routes/ (the leading underscore tells Vercel not to deploy those files as functions) and a single api/router.ts dispatches to them. A test in tests/api-plugin.test.ts fails if anyone adds a second function or forgets to register a route.

3The life of a request

Every API call follows the same path. Once you know it, any endpoint is easy to trace.

3.1Step by step

  1. Rewrite. vercel.json has two rewrites. /api/:path(.*) becomes /api/router?__path=:path; everything else becomes /index.html so client-side routes work.
  2. Rebuild the original request. originalRequest() in api/router.ts reads __path, deletes it from the query string, restores url.pathname = /api/<path>, and re-creates the Request with the same method, headers (including Cookie and Origin) and body bytes. Handlers therefore see their real URL and query string.
  3. Cross-site check. crossSite() rejects any non-GET request whose Origin is another site with 403 {"error":"cross_site_request"} (Section 9.5).
  4. Match. ROUTES is an ordered list of [pattern, module]. Each pattern compiles to ^pattern/?$ with :id replaced by [^/]+. Order matters: static segments come before :id, so /api/listings/analyze never matches /api/listings/:id. No match gives 404 {"error":"not_found"}; a module without that method export gives 405 {"error":"method_not_allowed"}.
  5. Handle. Each route module exports GET and/or POST, each wrapped in route() from api/_lib/http.ts. Handlers throw instead of building error responses. JSON bodies are read with readJson(), which rejects any body not sent as Content-Type: application/json with 415 and malformed JSON with 400.
  6. Wrap errors. route() turns a thrown HttpError(status, message) into {"error": message} with that status; a RateLimitError (a subclass carrying retryAfterSeconds) into 429 {"error":"rate_limited","message","retry_after"} plus a Retry-After header; a ZodError into 400 {"error":"invalid_request","issues":[…]}; anything else into a logged 500 {"error":"internal_error"}. Stack traces never reach the client.
  7. Respond. json(data, status) sets content-type: application/json and cache-control: no-store. Public, non-personal reads opt in to CDN caching with publicCache(response, seconds), which sets public, max-age=0, s-maxage=N, stale-while-revalidate=10N: /api/areas 1 h, /api/listings 30 s, /api/listings/:id and /:id/complete 60 s. Everything personal or date-sensitive (search, contact, availability, bookings, me, notifications, auth) stays no-store.

3.2Anatomy of a route module

// api/_routes/listings/[id]/contact.ts
export const GET = route(async (request) => {
  const id = listingIdFrom(request)          // zod uuid check, else 404 without touching the DB
  const { data, error } = await db().from('listings')
    .select('owner_name, owner_contact').eq('id', id).maybeSingle()
  if (error) throw error                    // becomes 500 internal_error
  if (!data) throw new HttpError(404, 'Listing not found')
  return json(data)
})

3.3Local development parity

npm run dev starts Vite with the plugin in dev/api-plugin.ts. The plugin copies every variable from .env.local into process.env (mirroring Vercel’s server-side env), converts Node’s IncomingMessage into a Web Request, loads api/router.ts through server.ssrLoadModule on every request (so edits hot-reload), and calls the router’s GET or POST. Because no __path is present, the router uses the URL as-is. The whole stack therefore runs locally without vercel dev.

Adding an endpoint

1) Create api/_routes/<name>.ts exporting GET/POST wrapped in route(). 2) Import it in api/router.ts and add a [pattern, module] row, with static segments above any :id sibling. 3) Server imports must end in .js (ESM on Vercel); tests/esm-imports.test.ts checks this. tests/api-plugin.test.ts fails if a route file is not registered.

The schema lives in supabase/migrations/ and is applied in filename order (SQL editor or supabase db push). Extensions are installed into the extensions schema per Supabase convention: vector (pgvector), postgis and btree_gist.

4.2Indexes and why each exists

  • listings_embedding_idx: HNSW on embedding vector_cosine_ops. Makes order by embedding <=> q_emb an approximate nearest-neighbour scan instead of a full sort.
  • listings_location_idx: GiST on the geography point. Serves st_dwithin radius filters.
  • listings_occasions_idx: GIN on occasions. Serves GET /api/listings?occasion=, which uses array containment (@>). The GiST location index also serves the <-> distance ordering in nearby_listings.
  • listings_created_at_idx, listings_owner_idx: newest-first lists and profile stats.
  • bookings_listing_dates_idx (listing_id, end_date): availability look-ups (“upcoming bookings of this listing”). bookings_borrower_idx (borrower_id, start_date): My Rentals.
  • notifications_user_idx (user_id, created_at desc): the bell’s newest-first query.

4.3Row-level security: on, with no policies

Every table has enable row level security and no policies. In Postgres that means the anon and authenticated roles can read and write nothing through Supabase’s public REST or GraphQL endpoints. Only the service role (which bypasses RLS) can touch data, and only the API holds the service-role key. The RPCs follow the same rule: revoke execute … from public, anon, authenticated and grant execute … to service_role. The consequence is simple: the only way to data is through /api, where validation and authorisation live.

4.4The constraint that makes double-booking impossible

create extension if not exists btree_gist with schema extensions;
constraint bookings_no_overlap exclude using gist (
  listing_id with =,
  daterange(start_date, end_date, '[]') with &&
) where (status = 'confirmed')

An exclusion constraint says “no two rows may have equal listing_id and overlapping date ranges”. btree_gist is what lets a GiST index handle the plain equality on a uuid alongside the range overlap. The range is inclusive on both ends ('[]'), so returning on the 12th and someone else picking up on the 12th is a conflict. Because the database enforces this atomically, two borrowers paying at the same instant cannot both win: the second insert fails with SQLSTATE 23P01, which the API maps to HTTP 409. Cancelled bookings are excluded from the check by the partial where.

4.6Browsing: nearest first, with paging

The home “nearby” row and Explore use GET /api/listings?area=&occasion=&limit=&offset= rather than search. With an area, the route calls nearby_listings with that area’s centroid, and results come back nearest first with distance_km. The RPC’s window count (count(*) over ()) becomes total, so the client knows when to stop paging. Explore pages 24 at a time. Without an area, the route falls back to newest first, with .range(offset, offset + limit − 1) and an exact count.

GET /api/listings?area=Adyar&occasion=wedding&limit=24&offset=0
200  cache-control: public, max-age=0, s-maxage=30, stale-while-revalidate=300
{ "listings": [ { "id": "…", "title": "…", "area": "Besant Nagar", "distance_km": 0.3, … } ], "total": 17 }

5Upload pipeline: photo to listing

Listing is a two-request conversation. POST /api/listings/analyze turns a photo into an editable draft; after the human edits it, POST /api/listings publishes it. Splitting them keeps a human in the loop: the model proposes, the lister decides.

5.1Step 1: check the caller, then read and sniff the image

Analyze requires a signed-in session (401 otherwise), or the server key in x-admin-key for the seed and readiness scripts, because every call spends AI quota and stores a photo. The UI therefore asks the lister to sign in before choosing a photo. The UI downsizes photos before upload, because Vercel rejects request bodies over 4.5 MB. The server enforces MAX_IMAGE_BYTES = 4 MB (413 otherwise). It never trusts the browser’s declared MIME type: sniffImage() in api/_lib/images.ts reads the first bytes.

TypeMagic bytes checkedStored as
JPEGFF D8 FF at offset 0.jpeg, image/jpeg
PNG89 then ASCII PNG.png, image/png
WebPRIFF at 0 and WEBP at 8.webp, image/webp
HEIC/HEIFftyp at 4, brand heic|heix|hevc|mif1|msf1|heif at 8.heic, image/heic

Anything else is 415 Unsupported image type, before any model is called.

5.2Step 2: store and tag in parallel

storeImage() uploads to the listings bucket at YYYY-MM-DD/<random uuid>.<ext> (upsert: false) and returns the public URL. At the same time analyzeImage() in api/_lib/vision.ts sends the image inline (base64) to Gemini with:

  • A system prompt with strict rules (VISION_SYSTEM_PROMPT): if the photo is not a rentable garment, return only {"is_clothing": false}; describe the garment, never the person, body or background; pick category, occasions and gender only from the controlled vocabulary, with disambiguation notes (e.g. ethnic_jacket is Nehru/bandhgala only; western tailored is blazer; if the photo shows a whole outfit, tag the most prominent rentable piece); 3–6 lowercase style tags; 1–3 colours; formality 1–5; a two-sentence description whose second sentence must say where the piece does not fit well (this makes search honest).
  • Structured output: responseMimeType: application/json with VISION_RESPONSE_SCHEMA (enums generated from shared/vocab.ts), temperature 0.2, thinkingLevel: minimal, 20-second timeout.
  • Normalise, then validate: normalizeVision() de-duplicates and lower-cases tags, caps list lengths and clamps formality into 1–5; then visionResultSchema (a zod discriminated union on is_clothing) validates the result.
  • One retry: withOneRetry() reruns generate + validate once if it throws. It does not retry a RateLimitError, because an immediate retry would spend another request from an exhausted quota.

5.3Step 3: decide the outcome

Promise.allSettled lets the route inspect both results. A storage failure is a real error. A rate limit deletes the photo and returns 429 so the UI can say “try again in N seconds”. Any other vision failure keeps the photo and returns 502 {"error":"analysis_failed","image_url"}, so the UI falls back to manual tagging with the already-stored image. A not-clothing verdict deletes the photo and returns 422.

// 200 OK — POST /api/listings/analyze

  "draft": {
    "title": "Maroon silk saree with gold zari border",
    "category": "saree", "gender": "women",

5.4Step 4: publish

POST /api/listings requires a signed-in session (seed scripts may instead send the server key; see Section 12). The body is validated by createListingSchema (the draft plus image_url, size, price_per_day 1–100000, area, owner_name, owner_contact). isOwnImageUrl() rejects any image URL that is not under <SUPABASE_URL>/storage/v1/object/public/listings/ (and any path containing ..), so listings can only show photos this app stored.

The server then computes the two fields the client must never send, in parallel:

  • Location from area. getArea() looks up the centroid and the insert writes location = 'SRID=4326;POINT(lng lat)'. Note the order: longitude first, as PostGIS expects.
  • Embedding from semantics only. embeddingText() joins title, category, occasions, style, colours and description. Size and price are deliberately excluded because they are SQL filters, not meaning.
// embeddingText() output, embedded with taskType RETRIEVAL_DOCUMENT
Maroon silk saree with gold zari border. saree. occasions: wedding, reception, festival.
style: silk, zari, traditional. colors: maroon, gold. A rich silk saree for weddings and
receptions. Too heavy for daytime college events.

The row is inserted with owner_id set to the session user and returned as 201 {"listing": {…public columns…}}. The write is synchronous, so the listing is searchable the moment the response arrives.

6Search pipeline: sentence to ranked matches

POST /api/search is the heart of DRAPE. The code is split into pure, unit-tested pieces: api/_lib/search-ai.ts (parser and reasons), api/_lib/ladder.ts (filters, fallback ladder, messages) and api/_lib/search.ts (orchestration).

// Request
POST /api/search
{ "query": "need something for a friend's sangeet, M, under ₹800", "area": "Adyar",
  "size": "M", "max_price": 800, "reasons": false }       // size, max_price, reasons optional

6.1Parse the sentence into filters

parseQuery() sends the raw text to the text LLM with PARSER_SYSTEM_PROMPT and a strict JSON schema. It must return exactly five keys, using null for anything not clearly stated (“never guess”):

{ "occasion": "sangeet_mehendi", "size": "M", "max_price": 800, "gender": null,
  "style_query": "festive, colourful outfit for a sangeet, comfortable to dance in" }

The prompt maps slang to vocabulary (“mehendi” → sangeet_mehendi, “rave/techno/EDM” → club_night, “1k” → 1000) and sets gender only when the message clearly says who it is for. style_query is the request rewritten as a description of the ideal outfit, with size and price removed. The result is validated by parsedQuerySchema with one retry. If the parser still fails, search degrades gracefully: all filters become null and style_query is the raw text.

6.2Merge with the UI chips

mergeFilters(): explicit size and max_price from the request (the UI’s chips) win over the parser; gender always comes from the parser; the area always comes from the header selector. The parsed object returned to the client reflects the merged values.

6.3Embed the intent

queryEmbeddingText() appends the occasion label to the style query, mirroring how listings are embedded: "festive … to dance in. occasion: Sangeet / Mehendi". It is embedded with gemini-embedding-001, taskType: RETRIEVAL_QUERY, 768 dimensions. The same embed() helper serves upload and search and rejects any vector that is not exactly 768-d, so dimensions cannot drift. Note that occasion is a ranking signal, not a filter.

6.4Filter and rank in Postgres

select …, st_distance(l.location, st_makepoint(q_lng, q_lat)::geography) / 1000 as distance_km,
       1 - (l.embedding <=> q_emb) as similarity
from listings l
where (q_size      is null or l.size = q_size or l.size = 'FREE')
  and (q_max_price is null or l.price_per_day <= q_max_price)
  and (q_gender    is null or l.gender in (q_gender, 'unisex'))
  and (q_lat       is null or st_dwithin(l.location, st_makepoint(q_lng, q_lat)::geography, q_radius_km * 1000))
order by l.embedding <=> q_emb
limit k;   -- k = RESULT_LIMIT = 12

<=> is pgvector’s cosine distance, so similarity = 1 − distance. Free-size pieces match any size, unisex pieces match either gender. The embedding is passed as a JSON string (JSON.stringify(embedding)), which PostgREST casts to vector.

6.5The fallback ladder and the match-quality floor

Vector search almost always returns something, so “zero results” alone would rarely trigger a fallback. Instead a step only counts as a hit if at least one result is a genuinely good match: isGoodEnough() requires a similarity ≥ MATCH_FLOOR (default 0.68, overridable by env). The last step accepts any non-empty result.

How 0.68 was chosen

Calibrated on gemini-embedding-001 over 14 real queries: plausible top matches scored 0.686–0.85, poor ones 0.59–0.66. The example that set the line: “wedding guest saree”, whose nearest item was a beige dress at 0.653. The floor sits in the gap. If you change the embedding model, re-calibrate (and re-embed every listing).

planAttempts() builds the steps (Figure 5); steps that would repeat the previous query are skipped (no budget step when there is no budget). Size and gender are never relaxed: a dress that does not fit is not a match. The step that produced the results drives relaxedMessage():

Step usedMessage (area Adyar, budget ₹800)
strictnull (nothing was relaxed)
wider_radiusNo good match under ₹800 within 10 km of Adyar, so here are options up to 25 km away.
no_budgetNo good match under ₹800 near Adyar, so here are options up to ₹1,200 within 25 km.
no_radiusNo good match under ₹800 within 25 km of Adyar, so here are the closest matches across Chennai, up to ₹1,200.

“Up to ₹1,200” is the highest price among the returned results, formatted with en-IN grouping. The wording says “no good match” rather than “nothing”, because the floor can relax a step that technically had weak results. The last step uses a 1000 km radius rather than none, so distance_km stays populated.

6.6“Why it fits”: batched reasons, results first

explainMatches() makes one LLM call for the top REASON_COUNT = 6 results (never one per card). The prompt asks for ≤ 12 words per item, specific to fabric, colour, silhouette or vibe; never mention size, price, distance or availability; never assume the wearer’s gender; be honest when an item is a weak fit. The server keeps only reasons whose id was in the request and trims each to 15 words (clampWords()). If the call fails, results are returned with reason: null; a reasons failure never fails a search.

By default (the PRD contract) reasons are inline. The UI sends "reasons": false so the grid renders as soon as matching is done (about 2 s), then calls POST /api/search/reasons:

POST /api/search/reasons   { "query": "…sangeet…", "ids": ["7f3c…", "a91d…"] }   // 1–6 uuids
200 { "reasons": [ { "id": "7f3c…", "reason": "Bright mirror-work lehenga made for twirling at a sangeet" } ] }

7.3The endpoint and the RPC

GET /api/listings/:id/complete loads the anchor’s category, derives its slot and pairing slots, and calls the RPC once per pairing slot in parallel: k = 4 for the completing slot, k = 2 for extras. Results are concatenated in priority order, tagged with their slot, and capped at 8.

select l.…, st_distance(l.location, a.location) / 1000, 1 - (l.embedding <=> a.embedding)
from listings a join listings l on l.id <> a.id
where a.id = anchor
  and l.category = any(pair_categories)                          -- complementary slot
  and (a.gender = 'unisex' or l.gender in (a.gender, 'unisex'))  -- gender-compatible
  and l.occasions && a.occasions                                -- share ≥ 1 occasion
order by (l.embedding <=> a.embedding)                           -- style distance
       + least(st_distance(l.location, a.location) / 1000, 30) / 300  -- nearness: 30 km costs 0.1
limit k;

The ranking is style first with a gentle nearness bonus: distance adds up to 0.1 to the cosine distance, capped at 30 km, so a slightly less similar piece next door can beat a perfect one across town.

8.4Mock payment, and how to make it real

export async function chargeAdvance(input: { amount: number; method: 'upi' | 'card' }): Promise<{ ref: string }>

To go live, replace the body with a real provider, for example a Razorpay order created server-side plus verification of the payment signature with the provider’s secret, and return the provider’s payment id as ref. The rest of the flow does not change. One thing to design deliberately when you do: today the charge happens before the insert, so a 409 after a real capture would need a refund or void. The usual fix is to authorise first and capture only after the insert succeeds, or to insert a pending row first.

9Accounts, sessions and Google sign-in

New design

DRAPE no longer uses Supabase Auth for accounts or sessions (it only brokers Google sign-in, Section 9.7). Accounts are rows in public.users, passwords are hashed by the API with Node’s scrypt, and sessions are opaque random tokens stored hashed in public.sessions and carried in an httpOnly cookie. Listings, bookings and notifications reference public.users. The browser never holds a readable token.

9.1Tables (migrations …0930000004_own_auth.sql, …0930000006_login_attempts.sql)

create table public.users (
  id            uuid primary key default gen_random_uuid(),
  created_at    timestamptz not null default now(),
  email         extensions.citext not null unique check (email ~ '…@…'),
  name          text not null check (length(name) between 1 and 80),
  password_hash text,          -- scrypt (or legacy bcrypt); null = Google-only
  google_sub    text unique    -- Google's stable account id, once linked
);
create table public.login_attempts (   -- …0930000006_login_attempts.sql
  email        extensions.citext primary key,  -- any email, registered or not
  failed       int not null default 0,
  locked_until timestamptz,
  updated_at   timestamptz not null default now()
);
create table public.sessions (
  token_hash text primary key,  -- hex SHA-256 of the cookie token
  user_id    uuid not null references public.users(id) on delete cascade,
  created_at timestamptz not null default now(),
  expires_at timestamptz not null
);  -- indexes: sessions_user_idx (user_id), sessions_expiry_idx (expires_at)

All three tables follow the house rule: RLS on, no policies, service role only. login_attempts has no foreign key on purpose: it counts attempts per email address, including addresses with no account. Migration …0006 also dropped the earlier per-user users.failed_logins and users.locked_until columns. The own_auth migration copies existing Supabase Auth accounts into public.users with the same ids and their bcrypt hashes (auth.users.encrypted_password), re-points the listings.owner_id, bookings.borrower_id and notifications.user_id foreign keys at public.users, and drops the Phase 7 profiles table and its on_auth_user_created trigger. Keeping the ids means every existing listing, booking and notification stays attached to the right person.

9.2Password hashing (api/_lib/passwords.ts)

  • scrypt (node:crypto) with a fresh random 16-byte salt per password, parameters N=16384, r=8, p=1, 64-byte key. The stored string is self-describing, scrypt$16384$8$1$<salt b64>$<hash b64>, so the cost can be raised later: a hash made with a different N is flagged needsRehash and upgraded at the next login.
  • Verification recomputes the hash with the stored parameters and compares with crypto.timingSafeEqual, so comparison time does not leak how many bytes matched. Passwords must be 8–200 characters.
  • Migrated accounts. Two teammates’ older accounts came from Supabase Auth with bcrypt hashes ($2a$/$2b$/$2y$). verifyPassword() checks those with bcryptjs and returns needsRehash: true; the login route then stores a fresh scrypt hash. After one login the account is indistinguishable from any other.

9.3Sessions (api/_lib/sessions.ts)

  • On sign-up or login, createSession() generates a 32-byte random token (base64url), inserts token_hash = SHA-256(token) with expires_at = now + 30 days, deletes that user’s already-expired sessions, and returns the cookie: 
    Set-Cookie: drape_session=<token>; Path=/; Max-Age=2592000; HttpOnly; SameSite=Lax; Secure
    Secure is omitted only for plain-http localhost/127.0.0.1, so local development works.
  • Every request that needs a user resolves it server-side: sessionUserId() reads the cookie, hashes it, looks up the session and rejects it if expires_at has passed; getUser() in api/_lib/auth.ts then loads id, email, name from users. requireUser() throws 401 "Please sign in first.". Handlers never accept a user id from the client.
  • Storing only the hash means a leaked database backup contains no usable session tokens.
  • Logout (POST /api/auth/logout) deletes the session row and returns an expired cookie (Max-Age=0), so the token is dead server-side even if a copy exists somewhere.

9.4Brute-force and enumeration protection (api/_routes/auth/login.ts)

  • Lockout, per email address. Each miss upserts public.login_attempts for that email and increments failed, whether or not an account exists. The 5th (MAX_FAILED_LOGINS) sets locked_until = now + 10 min (LOCK_MINUTES) and resets the counter. The lock is checked first; while locked, login returns 429 "Too many attempts for this email — try again in N min.". A successful login deletes the email’s row.
  • No email enumeration. An unknown email, and a Google-only account with no password, both run burnPasswordCheck(), a full scrypt verify against a dummy hash, so the response time matches a wrong password, and all three return the same 401 "Wrong email or password.". Because the lockout is keyed by email rather than by account, a 429 does not reveal whether an account exists either.

9.5CSRF defence

Because the session is a cookie, the API must make sure other sites cannot trigger state-changing requests with it. Three layers work together:

  1. SameSite=Lax cookies are not sent on cross-site POSTs.
  2. JSON-only POST bodies. readJson() rejects any body whose Content-Type is not application/json with 415. An HTML form on another site cannot send that type without a CORS preflight, which the API never grants.
  3. Origin check in the router itself: crossSite() in api/router.ts runs before route matching. A non-GET request whose Origin host differs from the request host (x-forwarded-host / host) gets 403 {"error":"cross_site_request"}. Requests with no Origin (server-side scripts) and GET/HEAD are unaffected.

9.7Google sign-in (Supabase Auth as a PKCE broker)

Google is a secondary option, and it is the only place Supabase Auth still appears. Supabase’s Google provider runs the Google consent flow for us; DRAPE then takes the verified identity, links or creates a row in its own public.users table, and starts its own drape_session cookie. The Supabase session that comes back is discarded, so auth.users acts purely as a Google broker. Google’s client ID and secret are configured in the Supabase dashboard, not in DRAPE’s environment.

Why PKCE, and what it protects

  • Binding to the browser. drape_oauth_verifier is httpOnly, scoped to Path=/api/auth, and lives 10 minutes. The token exchange at step ⑦ only succeeds with the verifier whose SHA-256 matches the challenge sent at step ②, so the callback is tied to the browser that started it (login-CSRF and code-injection protection).
  • No tokens in the browser. The code exchange is server-to-server; the Supabase access/refresh tokens are read once for the user’s identity and then thrown away.
  • Verified identities only. exchangeCode() in api/_lib/google.ts posts { auth_code, code_verifier } with the service-role apikey, requires a google identity and a confirmed email (email_confirmed_at), else the callback redirects to /?auth_error=google_unverified.
  • Linking. The user is matched by google_sub (the Google identity’s sub) first, then by email, in which case google_sub is attached to the existing row; otherwise a new user without a password is created. Such an account can only sign in with Google; a password login for it gets the generic 401.

Configuration (Supabase dashboard, not env vars)

  • Authentication → Providers → Google: client ID and secret from Google Cloud, with the Google-side authorised redirect URI https://<project>.supabase.co/auth/v1/callback.
  • Authentication → URL Configuration → Redirect URLs: DRAPE’s /api/auth/google/callback on production and on localhost, so Supabase will redirect back to it.
  • GET /api/auth/providers returns google: true only when Supabase’s public auth settings report the Google provider as enabled; otherwise the UI hides the button.

10Notifications

Owners learn about bookings through the bell in the header. The design goal: a booking can never exist without its notification. That is why the notification is written by a trigger, inside the same transaction as the booking insert, rather than by a second API call that could fail halfway.

create or replace function public.notify_owner_of_booking()
returns trigger language plpgsql security definer set search_path = '' as $$
declare owner uuid;
begin
  select owner_id into owner from public.listings where id = new.listing_id;
  if owner is not null and new.status = 'confirmed' and owner is distinct from new.borrower_id then
    insert into public.notifications (user_id, type, booking_id) values (owner, 'booking_received', new.id);
  end if;
  return new;
end $$;
create trigger on_booking_created after insert on public.bookings for each row execute function public.notify_owner_of_booking();

No notification is created for unowned (seed) listings, for non-confirmed rows, or when an owner books their own piece (the API also blocks that with a 400). If the insert fails, for example on the no-overlap constraint, the notification is rolled back with it.

10.2Delivery: polling

There is no websocket or push. While signed in, src/App.tsx calls GET /api/notifications immediately, then every 30 seconds, and whenever the tab regains focus. Worst-case latency is therefore about 30 s, which is fine for “someone booked your lehenga”. Moving to Supabase Realtime or web push later would not change the trigger or the table.

11.1Why OpenAI handles search text

The Gemini free tier allows 15 requests per minute per model. Uploads need one vision call and one embedding; each search needs an embedding plus two text calls (parser and reasons). If search text also used Gemini, a handful of searches in one minute could block uploads, and vice versa. So the search-time text calls go to OpenAI, which has separate and much higher limits, and Gemini is reserved for vision and embeddings.

textJson() tries OpenAI (Chat Completions, response_format: json_schema with strict: true) when OPENAI_API_KEY is set. If the key is missing, or OpenAI errors or times out, it logs a warning and calls Gemini with the equivalent OpenAPI-subset schema. Each prompt therefore carries two schemas describing the same shape (PARSER_JSON_SCHEMA / PARSER_GEMINI_SCHEMA, and likewise for reasons).

11.3429 handling

When Gemini returns HTTP 429, call() in gemini.ts reads the “retry in N s” hint from the error message (default 30 s) and throws RateLimitError(N). withOneRetry() deliberately does not retry it. route() turns it into:

HTTP/1.1 429 Too Many Requests
retry-after: 17
{ "error": "rate_limited", "message": "AI is busy — try again in 17s", "retry_after": 17 }

The UI shows “try again in N seconds”. The seed and retag scripts read retry_after, sleep, and retry (up to 5–6 times), which is how 79 listings were seeded on the free tier.

13.5Known limitations

  • Negation is not understood. “No sarees” cannot exclude sarees; semantic search has no “not”. The reasons line does call out the mismatch.
  • Occasion is not a hard filter, only a ranking signal via the embedding.
  • Free-tier quotas. Gemini at 15 RPM per model limits upload bursts. Note that GEMINI_VISION_MODEL and GEMINI_TEXT_MODEL default to the same model, so by default the Gemini text fallback (used when OpenAI is missing or failing) shares the vision quota. This is deliberate (the separate-quota model tried instead timed out); set GEMINI_TEXT_MODEL to change it.
  • Orphaned photos. Analyzed-but-never-published uploads (and verify-prd runs) leave files in Storage. README.md has a SQL query that lists them.
  • Payments are mocked, and the charge precedes the insert (see 8.4).
  • No cancellation endpoint yet, although the schema supports status = 'cancelled'.
  • Notifications poll every 30 s; no push.
  • Location is area-level: 15 fixed centroids, no real geolocation; everything in one area is 0 km apart.
  • The contact-reveal endpoint is public by design (the free contact reveal), so it is not rate-limited per user.

TermMeaning in DRAPE
AnchorThe listing a “Complete the look” request starts from.
Cosine similarity1 − (a <=> b); how close two embeddings point. Higher is more alike.

EmbeddingA 768-number vector representing meaning, from gemini-embedding-001. Documents use RETRIEVAL_DOCUMENT, queries RETRIEVAL_QUERY.
Exclusion constraintA Postgres constraint forbidding two rows whose values conflict under given operators (here: same listing and overlapping dates).
Fallback ladderThe sequence strict → wider radius → no budget → anywhere used when a step has no good match.
HNSWHierarchical navigable small-world graph: pgvector’s approximate nearest-neighbour index.

PKCEProof Key for Code Exchange: the OAuth client keeps a random verifier and sends only its hash; the code can be redeemed only with the verifier. Used for Google sign-in.
PostGIS / geographyGeo extension; geography(point, 4326) stores lat/lng and measures in metres.
